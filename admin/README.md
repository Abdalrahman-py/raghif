# لوحة تحكم رغيف (Admin Panel)

لوحة ويب بسيطة للمبرمج: HTML + CSS + Vue 3 من CDN، **بلا خطوة بناء ولا npm**.
الخطة والقرارات: [`docs/superpowers/plans/2026-11-04-admin-panel.md`](../docs/superpowers/plans/2026-11-04-admin-panel.md).

## الملفات

| الملف | الدور |
|---|---|
| `index.html` | الصفحة والقوالب (عربي RTL) |
| `app.js` | منطق الواجهة (Vue) |
| `api.js` | كل ما تطلبه اللوحة من Supabase (الوحيد الذي يعرف عنه شيئًا) |
| `config.js` | رابط المشروع والمفتاح **العام** + مفتاح `announcementsReady` |
| `style.css` | التصميم، بألوان التطبيق |
| `dev-mock.js` | بيانات تجريبية للتطوير فقط (`?mock=1` على localhost) |

## الأمان

- المفتاح في `config.js` هو المفتاح **العام (publishable)** نفسه الذي داخل الـ APK. **لا تضع `service_role` أبدًا** في هذا المجلد.
- الحماية ليست إخفاء الرابط: كل دوال `admin_*` في قاعدة البيانات ودالة `admin-api` تتحقق أن المستخدم المسجَّل مسؤول (`is_admin()`).
- رمز الـ PIN الذي يُنشأ يظهر مرة واحدة في الذاكرة فقط، ولا يُخزَّن في المتصفح.
- مكتبتا Vue وsupabase-js محمّلتان بإصدار محدد مع `integrity` (SRI).

## التجربة محليًا بلا خلفية

```bash
cd admin
python -m http.server 8099 --bind 127.0.0.1
```

ثم افتح <http://localhost:8099/?mock=1> وسجّل الدخول بأي بريد وكلمة المرور `demo`.
(`?mock=1` لا يعمل إلا على `localhost` أو `127.0.0.1`.)

## تشغيلها على الخلفية الحقيقية

تحتاج بالترتيب (المرحلة 7 في الخطة):

1. تطبيق migrations الستة الجديدة على Supabase.
2. نشر الدوال: `admin-api` (مع التحقق من JWT)، و`send-push` (مع `--no-verify-jwt`)، و`auth-gateway` المعدّل.
3. إنشاء حساب المسؤول (مرة واحدة، انظر القسم التالي).
4. فتح الصفحة (من `index.html` مباشرة أو من GitHub Pages) وتسجيل الدخول.

## إنشاء حساب المسؤول

حساب المسؤول مستخدم عادي في Supabase Auth يُضاف رقمه إلى جدول `admins`. لا توجد واجهة لإضافة مسؤول، وهذا مقصود: لا يمكن لأي لوحة أو تطبيق منح الصلاحية.

1. في لوحة Supabase: **Authentication → Users → Add user → Create new user**. أدخل بريدك وكلمة مرور **قوية وفريدة**، وفعّل **Auto Confirm User**.
2. في **SQL Editor** نفّذ (بعد تطبيق migrations 1–6، وبريدك مكان المثال):

   ```sql
   insert into public.admins (user_id)
   select id from auth.users where email = 'you@example.com';
   ```

   يجب أن تُرجع `INSERT 0 1`. إن أرجعت `INSERT 0 0` فالبريد غير مطابق.
3. افتح اللوحة وسجّل الدخول. إن قالت «هذا الحساب ليس حساب مسؤول» فالصف لم يُضف.

تحصين اختياري يُنصح به: من **Authentication → Providers → Email** عطّل «Allow new users to sign up» حتى لا يستطيع أحد إنشاء حسابات Auth من الخارج. التطبيق لا يعتمد عليه (البوابة `auth-gateway` تنشئ الحسابات بمفتاح الخدمة)، لكن **جرّب تسجيل مشترٍ جديد من التطبيق بعد تغييره** للتأكد. لا تغيّره قبل ذلك.

## النشر على GitHub Pages

`.github/workflows/admin-pages.yml` ينشر اللوحة عند أي تعديل على `admin/` في `master` (ويمكن تشغيله يدويًا). مرة واحدة فقط: **Settings → Pages → Source = GitHub Actions**. المستودع يجب أن يكون **عامًا** (Pages على مستودع خاص يحتاج خطة مدفوعة).

ينسخ الـ workflow خمسة ملفات فقط (`index.html`, `app.js`, `api.js`, `config.js`, `style.css`): لا `dev-mock.js` ولا هذا الملف. ويفشل إن وجد في الملفات المنشورة مفتاحًا سريًا (`sb_secret_…` أو أي JWT).

الصفحة عامة، لكن بدون حساب المسؤول لا ترى أي بيانات ولا تستطيع تنفيذ أي إجراء. أضفنا `noindex` لمنع الفهرسة.

## الإعلانات

زر إرسال الإشعارات معطّل افتراضيًا (`announcementsReady: false` في `config.js`) لأن نسخة التطبيق الحالية لا تستطيع عرض إشعار بلا حجز. فعّله بعد إصدار التطبيق المحدّث (المرحلة 6).
