# خطة لوحة تحكم المبرمج (Admin Panel)

تاريخ الخطة: 2026-11-04. الحالة: **المراحل 1 إلى 6 مكتوبة ومختبَرة محليًا (6 ما عدا بند التوثيق)؛ لا شيء مطبَّق أو منشور.**

## الهدف

لوحة ويب بسيطة (HTML + CSS + Vue 3 من CDN، بلا خطوة بناء) يستخدمها المبرمج وحده لـ:

- إنشاء حسابات أصحاب المخابز وإدارتها (المخبز وصاحبه كيان واحد).
- رؤية المشترين والتحكم بحساباتهم.
- متابعة الإحصائيات المهمة في التطبيق.
- إرسال إشعارات (تلقائية ويدوية) عبر FCM.

## القرارات المتفق عليها

| الموضوع | القرار |
|---|---|
| الدخول | حساب مسؤول واحد في Supabase Auth (بريد + كلمة مرور). اللوحة تستخدم **المفتاح العام فقط**. |
| الصلاحية | جدول `admins` + دالة `is_admin()`. كل دوال الإدارة تتحقق منها. أعمال `service_role` تمر عبر Edge Function `admin-api`. |
| الاستضافة | GitHub Pages (يتطلب مستودعًا عامًا، وإلا Cloudflare Pages). workflow ينشر عند تغير `admin/` فقط. |
| الواجهة | عربية RTL، بألوان التطبيق (أزرق رمادي فاتح + بني) وخط IBM Plex Sans Arabic. |
| المخبز وصاحبه | كيان واحد: نموذج واحد ينشئ الحساب والمخبز معًا. `stores.owner_id` يبقى. |
| لا حذف نهائي | تعطيل وأرشفة فقط. الحجوزات والسجلات لا تُمس. المخبز: `active` / `paused` / `archived`. المشتري: `active` / `disabled`. |
| الـ PIN | يُولَّد عشوائيًا (4 أرقام) ويظهر **مرة واحدة** مع زر نسخ. صاحب المخبز يغيّره من التطبيق (الرمز الحالي + الجديد مرتين، على السيرفر، بحد للمحاولات). المشتري لا يغيّره الآن. |
| سعر الربطة | `stores.bag_price` ثابت 3 شيكل افتراضيًا، قابل للتعديل لكل مخبز. الإيراد = المستلم × السعر (تقدير، لا مدفوعات حقيقية). |
| الإشعارات | كل صف جديد في `notification_inbox` يُرسَل push تلقائيًا. إرسال يدوي من اللوحة (لمخبز أو للجميع). |
| تطبيق الـ migrations | أكتبها وأختبرها فقط. **لا يُطبَّق شيء على القاعدة الحية بلا موافقة صريحة على كل دفعة.** |

### سلوك حالات المخبز

| الحالة | يظهر للمشترين | الحجز | تسجيل دخول الصاحب |
|---|---|---|---|
| active | نعم | نعم (إن فتحه صاحبه بـ `is_open`) | نعم |
| paused | نعم + شارة "متوقف مؤقتًا" | لا | نعم (يرى لوحته، لا يفتح البيع) |
| archived | **لا** (إلا لمن له حجز قديم فيه) | لا | **لا** |

`is_open` يبقى قرار صاحب المخبز اليومي، وحالتك فوقه كصمام أمان.
المشتري `disabled`: لا يسجّل الدخول ولا يحجز.

## الإحصائيات المطلوبة

- **عامة:** عدد المشترين والمخابز، المسجلون الجدد (يوم / أسبوع / شهر)، حجوزات اليوم (المستلمة / غير المستلمة)، إجمالي الأكياس المباعة، الإيراد التقديري.
- **لكل مخبز:** المبيعات اليومية، نسبة الاستلام، المتبقي، الأكثر مبيعًا، الراكدة (لا حجوزات منذ N أيام).
- **المشترون:** قائمة وبحث وعدد الحجوزات لكل مشترٍ، من لم يستلموا مرارًا، حالة التحقق.
- **النظام:** الإشعارات المرسلة، سجل المسح (`scan_events`)، رسم بياني لحجوزات آخر 30 يومًا.

## ملاحظات من فحص القاعدة الحية (2026-11-04)

- `authenticated` يملك صلاحيات **على مستوى الجدول** (INSERT/UPDATE/DELETE) على `stores`. لذلك أي عمود جديد (`status`, `bag_price`) يصبح قابلًا للتعديل من صاحب المخبز نفسه ما لم نمنعه. الحل: trigger يرفض تغييرهما من غير المسؤول.
- `authenticated` يملك `DELETE` على `stores` و`profiles`، وحذف مخبز أو ملف شخصي يحذف بالتتالي كل حجوزاته. يُسحب `DELETE` (لا حذف نهائي).
- `verification_status` ما زال قابلًا للتعديل من العميل (ثغرة موثقة في `AGENTS.md`). تُعالَج في مرحلة التطبيق (6) بنقل التغيير إلى RPC وسحب الصلاحية.
- `profiles.verification_status` يقبل `pending` و`verified` فقط. لا نضيف `rejected` الآن (التطبيق لا يفهمه)؛ الرفض = إبقاء `pending` + تعطيل الحساب.
- `notification_inbox.kind` يقبل `confirmed` و`ready` و`postponed` فقط؛ نضيف `announcement`.
- لا توجد بيئة SQL محلية (لا docker ولا psql) على هذا الجهاز. اختبارات SQL تُكتب بنفس أسلوب `tests/*.sql` وتُشغَّل في `tests/run.sh` عند توفر docker، أو تُجرى كتجربة داخل transaction يُتراجع عنها (rollback) بعد موافقتك.

### المرحلة 3 — الإشعارات عبر FCM ← **مكتوبة (غير منشورة)**

**ما أُنجز:**
- `functions/send-push/` (`core.ts` + `index.ts` + 9 اختبارات): تستقبل `{inboxId}` من trigger، تقرأ صف `notification_inbox`، وترسل عبر FCM إلى كل أجهزة صاحبه برسالة تحمل `kind` و`inboxId`، وتحذف الرموز التي ترفضها Firebase كمنتهية (UNREGISTERED/404) وتُبقي ما فشل مؤقتًا. تُصادق بنفس سرّ `NOTIFY_BATCH_SECRET` وتفشل مغلقة إن لم يُضبط، وتتراجع إلى `sent:0` إن لم يوجد `FCM_SERVICE_ACCOUNT`.
- migration `20261104105000_inbox_push_trigger.sql`: trigger على `notification_inbox` يستدعيها، وأي فشل فيه يتحول إلى تحذير فلا يلغي الحجز أو التأجيل. اختباره `tests/inbox_push.sql` (7 فحوص: النوعان المعنيان يدفعان، والآخران لا، وغياب السر لا يضيّع الصف).

**قرار تصميمي:** الـ trigger يدفع نوعين فقط: `postponed` و`announcement`. النوعان `confirmed` و`ready` يُدفعان فعلًا من trigger_notify_purchase وtrigger_notify_batch عبر notify-batch؛ دفعهما من هنا أيضًا كان سيهز الهاتف مرتين. بهذا يُغلق ثغرة "التأجيل لا يرسل push". توحيد الأنواع الأربعة في مسار واحد ممكن لاحقًا لكنه يعدّل دالة حية تعمل.

**للنشر:** `supabase secrets set FCM_SERVICE_ACCOUNT=...` إن لم يكن مضبوطًا، ونشر `send-push` بـ `--no-verify-jwt`، قبل تطبيق migration 6 أو بعده (الـ trigger لا يفشل إن لم تكن الدالة منشورة).

**حدّ معروف:** الإعلان لـ N مستخدمًا ينتج N طلب HTTP متتالٍ من pg_net؛ مقبول للحجم الحالي، ويُجمَّع في طلب واحد إن كبر.

**كانت الخطة الأصلية:**

- Edge Function `send-push`: تأخذ صف `notification_inbox` وترسل إلى `device_tokens` للمستخدم عبر FCM (تعيد استخدام منطق `notify-batch`).
- trigger على `notification_inbox` (بعد الإدراج) يستدعيها عبر `pg_net` بنفس سر Vault.
- يغلق ثغرة "التأجيل لا يرسل push".
- يتطلب سر `FCM_SERVICE_ACCOUNT` في Supabase (غير مؤكد وجوده).

### المرحلة 6 — تعديلات التطبيق ← **منجزة ما عدا بند التوثيق**

**ما أُنجز (Dart، 291 اختبارًا ناجحًا، `flutter analyze` نظيف):**
- **تغيير الـ PIN للمالك:** `ChangePinSheet` (رمز حالي + جديد + تأكيد، 4 أرقام، أخطاء الخادم بالعربية: خاطئ / مقفل / ضعيف / مطابق للحالي / لا اتصال)، وزرها في شاشة الحساب **للمالك فقط**، عبر `AuthRepository.changePin` → RPC `change_my_pin`. أي كلمة غير معروفة من الخادم تُعامل كرفض لا نجاح.
- **رسائل الدخول:** بوابة الدخول ترد 403 فيُرمى `AccountBlockedException` ويعرض التطبيق «تم تعطيل هذا الحساب» أو «هذا المخبز غير متاح حاليًا» بدل «رمز خاطئ» أو «لا اتصال». (يعمل في مسارات PIN والرمز والجوال.)
- **حالة المخبز:** `StoreModel.status` (active/paused/archived) تُقرأ من `stores.status`؛ `canPurchase` يشترط `active`. شارة «متوقف مؤقتًا» (بلون التحذير) و«غير متاح» للمؤرشف في القائمة والتفاصيل. الخادم القديم بلا العمود يعني «فعّال».
- **إشعار بلا حجز:** `AppNotification.purchaseId` صار اختياريًا. الإعلان يُعرض ويمكن «تعليمه كمقروء» ولا يفتح حجزًا ولا ينهار التطبيق. **هذا ما يسمح بتفعيل `announcementsReady` في اللوحة بعد إصدار هذه النسخة.**

**لم يُنفَّذ: نقل `verification_status` إلى RPC وسحب الصلاحية.** هذا قرار منتج لا تقني: التوثيق اليوم يحاكى في التطبيق ويقلب المشتري حالته بنفسه. بعد وجود اللوحة هناك خياران: (أ) إبقاء المحاكاة وتغليفها بـ RPC (لا يتغير سلوك المشتري، لكن لا أمان حقيقي)، أو (ب) جعل التوثيق **بيد المسؤول فقط** فيبقى المشتري «بانتظار التوثيق» حتى تقبله من اللوحة (أمان حقيقي، لكن يغيّر تجربة التسجيل). ينتظر قرارك.

**كانت الخطة الأصلية:**

- شاشة تغيير الـ PIN (للمالك فقط) في شاشة الحساب.
- شارة "متوقف مؤقتًا" للمخبز عند المشترين، والتعامل مع رسالة "حساب معطل".
- نقل تغيير `verification_status` إلى RPC وسحب الصلاحية (إغلاق الثغرة الموثقة).
