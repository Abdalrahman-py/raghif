## The one thing to understand first

The app runs **two parallel queue implementations that never meet**:

1. **LIVE: `QueueController`** — an in-memory `ChangeNotifier` with hardcoded
   demo stores (45/120/0 bags), built bare in `main.dart:33`, used by EVERY
   screen (store list, purchase, confirmation, owner dashboard, owner queue).
   All purchases live in RAM — app restart = everything gone. No purchase is
   ever written to disk.
2. **DEAD: `QueueRepositoryImpl`** (drift/sqlite, 314 lines, fully
   implemented, registered in DI, passes 4 tests) — referenced by zero
   screens. Its data is seeded but never read by the UI.

So issue #7 ("replace mock data with real drift queries") is not a small gap:
it is an architectural unification with semantic conflicts underneath.
Roughly a third of `lib/` is dead or speculative (retrofit/Dio/ApiService
layer + committed `.g.dart`, the drift queue layer, domain
`StoreModel`/`PurchaseModel` duplicates, `QrPayload` with zero importers).

## Rule conflict the audit exposed (product decision needed)

One-bag-per-day: spec.md says **across ALL stores** — drift schema enforces it
(`UNIQUE(user_id, purchase_date)`, genuinely enforced + tested). The live mock
enforces **PER STORE** (queue_controller:74-86) and the UI string says "من هذا
المخبز اليوم" while onboarding copy says one per ID daily. Mock contradicts
the schema, which contradicts the string. Spec-side global-per-day is correct,
but worth confirming with the repo owner for the 1-store pilot.

## Decisions (owner answers, 2026-09-05)

A. **One-bag-per-day: default = per user / per national ID / per day, NOT per
   store** (matches spec + drift `UNIQUE(user_id, purchase_date)`). But build
   it as a changeable policy: the rule must be a single seam that can later be
   scoped per store or made store-owner-settable. Mock's per-store logic and
   the "من هذا المخبز اليوم" string are WRONG vs the decision — fix in the
   #7 unification (global enforcement is the default; the mock layer gets
   deleted, so the wrong copy dies with it).
B. **Verification flow (ID photo + selfie + waiting): KEEP and document.**
   It is the verification mockup — deliberately part of the flow. Needs a
   spec.md section so it stops being undocumented scope creep. (Still to fix:
   discard-the-photo honesty is fine for a mock, but the gate needs an escape
   affordance — see P0 tasks.)
C. **Confirmation screen: plain-language "you'll be notified", not the
   invented ETA.** Replace the estimated ready time with a plain
   "سيتم إعلامك عندما تكون دفعتك جاهزة" style statement. The
   `estimatedReadyAtMillis`/`formatReadyTime` helpers become dead code if
   nothing else uses them — remove rather than keep.
D. **Notifications: NOT in this workstream.** The app must eventually inform
   users about their bag / order status / batch release — but that is someone
   else's scope (SMS/push delivery). Our side only produces the state
   transitions (batch → notified) that the notification layer consumes.
   Leave flutter_local_notifications installed for whoever owns it.
E. (still open) Batch release discipline: after collected (spec) vs as soon
   as previous batch is notified (current code).
F. (still open) Extra registration fields (name, Jawwal number) — keep as
   decided extras?
